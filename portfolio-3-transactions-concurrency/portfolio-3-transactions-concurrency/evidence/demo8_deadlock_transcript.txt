Demo: demo8_deadlock
Two separate connections: Session 1 id=85, Session 2 id=86

===== STEP 1  (Session 1) =====
  # Part A. Reset. Transfer 1 (Alice -> Bola) debits Alice: this LOCKS Alice's row.
  > USE arcledger;
  > CALL sp_reset_demo();
  > SET @A = (SELECT account_id FROM account WHERE account_number = '9000000001');
  > SET @B = (SELECT account_id FROM account WHERE account_number = '9000000002');
  > START TRANSACTION;
  > UPDATE account SET balance = balance - 10000 WHERE account_id = @A;
   OK (1 row(s) affected)

===== STEP 2  (Session 2) =====
  # Transfer 2 (Bola -> Alice) debits Bola: this LOCKS Bola's row.
  > USE arcledger;
  > SET @A = (SELECT account_id FROM account WHERE account_number = '9000000001');
  > SET @B = (SELECT account_id FROM account WHERE account_number = '9000000002');
  > START TRANSACTION;
  > UPDATE account SET balance = balance - 20000 WHERE account_id = @B;
   OK (1 row(s) affected)

===== STEP 3  (Session 1) =====
  # Transfer 1 now credits Bola - but Bola's row is locked by Session 2, so Session 1 WAITS. Leave it running and go to Session 2, step 4.
  > UPDATE account SET balance = balance + 10000 WHERE account_id = @B;
   ... Session 1 is WAITING for a lock held by the other session ...

===== STEP 4  (Session 2) =====
  # Transfer 2 now credits Alice - but Alice is locked by Session 1, which is waiting for Session 2. Neither can ever continue: a DEADLOCK. MySQL detects it immediately and rolls this transaction back. ERROR 1213 here is EXPECTED.
  > UPDATE account SET balance = balance + 20000 WHERE account_id = @A;
   ERROR 1213: Deadlock found when trying to get lock; try restarting transaction

... Session 1, STEP 3 RESUMED - the lock it was waiting for was released:
   OK (1 row(s) affected)
   (this statement waited 2.3 s for a lock)

===== STEP 5  (Session 1) =====
  # Session 1's step 3 has completed: Session 2 was chosen as the deadlock victim. Commit. Only Transfer 1 happened: Alice 90,000, Bola 110,000. The application must retry Transfer 2.
  > COMMIT;
  > SELECT * FROM v_demo_balances;
   +----------------+-------+-----------+--------+
   | account_number | owner | balance   | status |
   +----------------+-------+-----------+--------+
   | 9000000001     | Alice | 90000.00  | ACTIVE |
   | 9000000002     | Bola  | 110000.00 | ACTIVE |
   +----------------+-------+-----------+--------+

===== STEP 7  (Session 1) =====
  # Part B - THE FIX. Reset. Both transfers lock the two accounts in the SAME order (lowest account_id first), exactly as sp_transfer does.
  > CALL sp_reset_demo();
  > START TRANSACTION;
  > SELECT account_id FROM account WHERE account_id IN (@A, @B) ORDER BY account_id FOR UPDATE;
   +------------+
   | account_id |
   +------------+
   | 15001      |
   | 15002      |
   +------------+

===== STEP 8  (Session 2) =====
  # Transfer 2 locks in the SAME order (lowest account_id first). Alice's row is already locked by Session 1, so it WAITS - but waiting is not a deadlock. Leave it running and go to Session 1, step 9.
  > START TRANSACTION;
  > SELECT account_id FROM account WHERE account_id IN (@A, @B) ORDER BY account_id FOR UPDATE;
   ... Session 2 is WAITING for a lock held by the other session ...

===== STEP 9  (Session 1) =====
  # Transfer 1 completes and commits. Session 2's step 8 then finishes by itself. No deadlock - the second transfer simply waited its turn.
  > UPDATE account SET balance = balance - 10000 WHERE account_id = @A;
   OK (1 row(s) affected)
  > UPDATE account SET balance = balance + 10000 WHERE account_id = @B;
   OK (1 row(s) affected)
  > COMMIT;

... Session 2, STEP 8 RESUMED - the lock it was waiting for was released:
   +------------+
   | account_id |
   +------------+
   | 15001      |
   | 15002      |
   +------------+
   (this statement waited 2.3 s for a lock)

===== STEP 10  (Session 2) =====
  # Transfer 2 now runs and commits.
  > UPDATE account SET balance = balance - 20000 WHERE account_id = @B;
   OK (1 row(s) affected)
  > UPDATE account SET balance = balance + 20000 WHERE account_id = @A;
   OK (1 row(s) affected)
  > COMMIT;

===== STEP 11  (Session 1) =====
  # Both transfers succeeded: Alice 100,000 - 10,000 + 20,000 = 110,000; Bola 100,000 + 10,000 - 20,000 = 90,000.
